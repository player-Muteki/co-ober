# 差距分析验收项之一：多会话流隔离

日期：2026-10-18。实现版本：Co-Ober 0.2.69。

## 1. 参考仓库

Claudian `main` 仍为 `1e432bef` / 2.3.24（经镜像取回；github.com 直连仍不稳）。

## 2. 为什么挑这一项

差距分析第 7 阶段（可选原生 HTTP 纵向最小闭环）列了四条**验收**条件：

> 验收：多个标签不串流，失联不伪装正常完成，中断不留后台工作，
> 已提交请求不因 fallback 重复执行。

这四条是"打开后端之前必须成立"的前置条件。本轮取第一条，因为它是四条里
唯一**不需要中断、不需要杀进程**就能在一次测量里验完的，而另外三条都要
布置更多装置。

## 3. 实测：这条流确实是复用的

用一次 `opencode serve`，建**两个会话**，在**同一条**目录域事件流上同时发提示词，
两个提示词各带一个标记。实测结果：

- 两个标记**都出现在同一条流上**（等待条件要求两者同时出现才继续，实际满足）；
- 两个会话的帧在这条连接上**交错**；
- 按 `sessionID` 过滤后，各自组装的回答**都不含对方的标记**。

即：`GET /api/event?location[directory]=…` 是**按目录复用**的，会话之间并不隔离
通道。**"多个标签不串流"完全依赖客户端按 `sessionID` 过滤**，而不是依赖服务端
把流分开。

## 4. 本仓库现状

两个 reducer 都已经按 `sessionID` 过滤：

- `OpencodeStreamProbe.reduceNativeStream` —— `d.sessionID !== sessionID → continue`
- `OpencodeV2SliceProbe.reduceV2SliceEvents` —— `data.sessionID !== sessionId → continue`

因此这一条**本来就成立**。但没有任何测试钉住它：把过滤删掉，2510 项测试仍然全绿。

## 5. 顺带量出一个真实缺陷

测量方式本身暴露了一个探针问题。slice 探针的事件监听原本是：

```ts
collected.push(chunk);
if (collected.join('').length > SLICE_READ_MAX_CHARS) break;
```

**读预算按连接计，而不是按会话计。** 既然这条流是复用的，一个繁忙的邻居会话
就能先把预算耗尽，让本探针在自己的答案读完之前 `break`——读数于是安静地丢掉
一半证据，而面板上只会看到一个"没有回答"。

修法：预算只计**属于本会话的帧**（`ownFrameChars`），别人的帧和不带
`sessionID` 的 hydration 噪声一律不计价。逐帧成本用估算值即可——这个预算的
作用是让无限流停下来，估得偏一点只影响何时收手，不影响结论。

边界已确认能分辨新旧：把调用点改回 `chunk.length`（按连接计），测试失败，
`streamed` 变成 `false`——也就是**答案确实被邻居挤掉了**。

## 6. 顺带记下的一个小陷阱

写边界时先犯了一个自己刚在 0.2.68 修过的错：断言写成
`expect(content).toEqual({ __proto__: 'kept' })`。对象字面量里的 `__proto__`
设的是**原型**而不是键，于是断言了一个和被测行为无关的东西。已改为用
`Object.hasOwn` 断言。
