# 差距分析验收项之二：失联不伪装成"从未开始"

日期：2026-10-18。实现版本：Co-Ober 0.2.70。

## 1. 参考仓库

Claudian `main` 仍为 `1e432bef` / 2.3.24。

## 2. 目标

差距分析第 7 阶段的第二条验收：**失联不伪装正常完成**。
0.2.69 测过多会话隔离（第一条）。这一条要在**运行途中连接断掉**时，
报告不能看起来像"内核根本没跑起来"。

## 3. 实测尝试与它给出的东西

先按上一轮的办法搭了"运行中杀掉 serve"的装置（stub provider 挂起 20 秒，
第 3 秒 SIGKILL 服务端）。装置本身没有跑出干净结果——预算花在了搬运上，
而诚实的要求是不把没测成的东西写成测过。所以这一轮**没有**声称完成实测，
改为从代码路径上把问题钉死，并在发布说明与本文里明确标注实测仍待补。

代码路径是确定的，不依赖活的服务端：

```
poll loop:  requestFn(.../message)  ← 服务端已消失，这里抛错
   ↓ 异常逃出 run()
Promise.race([cancelled, run()]).catch(() => DEFAULT_SLICE)
   ↓
DEFAULT_SLICE = { status:'unavailable', enqueued:false, delivered:false, started:false, … }
```

也就是说：**一次已经入队、已投递、已开始执行的回合，在连接断掉后，
整份读数被换成"从未开始"的默认值**。三个已经证明的事实被一并抹掉，
面板随后会说"无法驱动原生会话 — 内核未能完成准备"。

这句话是错的，而且**指错方向**：准备完成了，回合跑起来了，掉的是链路。
读者据此会去查安装，而不是查连接。

这与 0.2.63 修过的目录 `unauthorized` / `did not answer` 是同一类：
一个**可命名**的观察，被压进一个读者无从分辨的桶。

## 4. 落地的边界

- `sliceStatus` 增加 `disconnected`，排在 `failed` 之后、`admitted` 之前：
  有具名错误仍然报 `failed`（那是内核自己的失败），只是链路断了才报
  `disconnected`。
- 轮询循环自己捕获连接层异常并跳出；**HTTP 状态码不算断线**——服务端还活着
  并且回答了，那是另一回事，继续按原路径抛出。
- 已观察到的 `enqueued` / `delivered` / `started` **留在读数上**。断线不撤销
  已经挣到的证据。
- 设置页新增一句独立文案，并把这三条腿一并显示。

边界两向都钉住：
- 中途断线 → `disconnected`，且三条腿仍为 true；
- 从未起来的内核 → 仍是 `unavailable`，且 `started` 为 false。
  这条防止修复把任何失败都染成"链路问题"。

把修复回退后，第一条边界按预期失败：状态是 `unavailable`。
